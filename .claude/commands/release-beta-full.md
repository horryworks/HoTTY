# /release-beta-full — ベータリリース一括実行

`/verify`・`/docs`・`/release-beta` を **この順で** 通し、途中で落ちたら止まる
ベータリリースの一括手順。各フェーズの中身はここに複製しない。必ず
既存のコマンド定義（`.claude/commands/verify.md`, `docs.md`, `release-beta.md`）を
そのまま実行すること。片方だけ更新されて食い違うのを防ぐため。

引数: `$ARGUMENTS`

## 引数

| 引数 | 意味 |
| --- | --- |
| `<バージョン>` | 付けるベータ版数（例 `2.1.0-beta2`）。省略時は `package.json` の現行版から次のベータ番号を提案し、確認を取る |
| `--from=verify\|docs\|release` | 途中フェーズから再開する。前フェーズは完了済みとみなす |
| `--skip-verify` | フェーズ 1 を飛ばす。**直前に `/verify` を通していて、その後コードを触っていない場合だけ**許可。理由を最終レポートに明記する |
| `--dry-run` | commit / push / tag を行わず、各フェーズが出す差分だけを提示して終わる |

## 事前チェック（フェーズ 0）

いずれか 1 つでも満たさなければ、**先に進まずユーザーに確認する**。

1. `git status --porcelain` が空であること。未コミットの変更があれば、
   それが今回のリリースに含めるべきものかを尋ねる。
2. 作業ブランチが意図したものであること（`git rev-parse --abbrev-ref HEAD`）。
3. バージョンが 3 ファイルすべてで一致していること。ここがリリースの単一の真実。
   - `package.json` の `version`
   - `src-tauri/tauri.conf.json` の `version`
   - `src-tauri/Cargo.toml` の `[package] version`
4. 指定バージョンのタグ／リリースノート見出しが既に無いこと
   （`git tag -l` と `RELEASE_NOTES.md` の `## v<バージョン>`）。あれば重複リリース。

## フェーズ 1 — `/verify`

`/verify` を実行する。

- **指摘が出たら、リリースを進める前にすべて直す。** 直したうえで `/verify` を
  もう一度通し、クリーンになるまで繰り返す（最大 3 巡）。3 巡で収束しなければ
  止まり、残っている指摘と原因の見立てを報告する。
- 修正コミットはリリースコミットと混ぜない。`0fd8857` と同様、
  `Fix /verify findings: <要約>` として別に積む。
- セキュリティ指摘は、リリースを遅らせてでも必ず先に潰す。「次のベータで」は無し。
- ここで直したものは、フェーズ 2・3 で書くべき内容でもある。何を直したかを
  控えておき、フェーズ 3 のリリースノートに反映する。

`--skip-verify` のときはこのフェーズを飛ばすが、最終レポートに
「`/verify` 未実行（理由: …）」と明示する。

## フェーズ 2 — `/docs`

`/docs` を実行する。

- 対象は英日そろえる。**片方だけ更新した状態で次へ進まない。**
  （`README.md` / `README.ja.md`、および `/docs` が扱う他のドキュメント）
- フェーズ 1 で直した内容が、ユーザーから見える挙動・設定・既定値を
  変えているなら、その反映漏れがないか確認する。
- 出た差分をユーザーに提示してから次へ進む。

## フェーズ 3 — `/release-beta`

`/release-beta` を、フェーズ 0 で確定したバージョンを渡して実行する。

このリポジトリの慣習として、少なくとも以下が揃っていることを確認する
（実際の作業は `/release-beta` の定義に従う。ここは抜けの検査用チェックリスト）。

- バージョン更新が **3 ファイルすべて**（`package.json` / `src-tauri/tauri.conf.json`
  / `src-tauri/Cargo.toml`）。`package-lock.json` の版数も追随していること。
- `RELEASE_NOTES.md` と `RELEASE_NOTES.ja.md` の **両方** に `## v<バージョン>` を追加。
  既存の節と同じ構成にする — 冒頭に何が変わったかの平文リード、続けて
  `### New Features` / `### Improvements` / `### Bug Fixes` / `### Security`
  （日本語版は `### 新機能` / `### 改善` / `### バグ修正` / `### セキュリティ`）。
  該当が無い見出しは書かない。日本語版は英語版の機械的な直訳ではなく、
  既存の節と同じ語り口に合わせる。
- コミットメッセージは 1 行目が `v<バージョン> <変更点をカンマ区切りで列挙>`
  （例: `v2.1.0-beta1 AI-opened terminals with per-request approval, ...`）。
- `--dry-run` なら、ここで commit / push / tag を行わず差分の提示で終わる。

## 最終レポート

完了したら、次を 1 つにまとめて報告する。

- リリースしたバージョンと、コミット／タグ／プッシュ先ブランチ
- 各フェーズの結果: `/verify`（巡回数と最終的にクリーンか）、`/docs`（更新ファイル）、
  `/release-beta`（変更ファイル）
- 飛ばしたもの・積み残し（`--skip-verify` を使った場合はその理由を含む）
- 次に人がやる必要があること（タグからのビルド、リリースページの作成 等）

## 中断ルール

以下ではリリースを続行せず、その時点で止まって報告する。

- `/verify` の指摘が 3 巡で収束しない、または未解決のセキュリティ指摘が残る
- 事前チェックの 3 ファイル間でバージョンが食い違い、どれが正しいか判断できない
- ドキュメントの英日いずれかしか更新できない
- 指定バージョンのタグ／リリースノート節が既に存在する

止まったときは、どのフェーズのどこで止まったかを言い、
`--from=<フェーズ>` で再開できることを添える。
